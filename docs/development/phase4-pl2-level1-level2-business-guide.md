# KOIKI Level 1 / Level 2 — 業務要件から見た選択とPL2検証の意味

**状態:** 説明・判断用DRAFT（2026-09-27）。業務アプリチームとの要件確認に使う。Level 2の採用、Phase 4の開始、DoD変更または正式配布を決定する文書ではない。

**現在地:** Phase 3のLevel 1はReferenceで実装・承認済み。Level 2はPhase 4の計画対象で、PL2の検証は非配布Toolingだけで実施した。実案件の通知要件、送信先、運用体制はまだ確認できていない。

## 1. 先に決めるのは「その業務が何を成功とするか」

KOIKIのLevel 1 / Level 2は、アプリ全体の品質や成熟度の等級ではなく、**業務モジュール間の処理をいつ成立させるか**に関する採用段階である。画面がMVCかRESTか、モジュールを分けられるかという判断とは別である。Spring Modulith製品の公式な等級を表す語でもない。

業務要件を次の順に確認する。

1. 受け手の判断・更新が失敗したとき、元の操作も失敗すべきか。**はい**なら同じ業務処理内の同期連携を選ぶ。
2. 元の操作は成功させ、その後で通知・外部連携を行うか。**はい**なら、連携が遅れる・失敗する状態を業務として許容できる時間を決める。
3. その副作用は、プロセス停止を挟んでも届ける必要があるか。**はい**なら処理待ちを保存し、復旧する仕組みが必要になる。
4. 送信結果が不明なまま再実行したとき、二重送信は許容できるか。許容できないなら、送信先を含む冪等性が必要になる。
5. 滞留を誰が検知し、いつまでに、どの権限・手順で復旧するか。答えられなければ、耐久配信を実運用の約束として提供できない。

同じ申請業務でも、承認可否の判断、業務監査、承認メールを一括して非同期化するわけではない。各処理が業務上どの時点で必須かによって分ける。

## 2. Level 1で実現すること、Level 2で増えること

| 業務上の問い | Level 1：現在の承認済み範囲 | Level 2：採用を検討する範囲 |
|---|---|---|
| 受け手が拒否したら元の操作も取り消すか | できる。同期の受け手が同じ業務トランザクションで判断する | この要件自体はLevel 1の同期処理を維持する |
| モジュールを分けながら連携できるか | できる。イベントで連携し、送り手は受け手の内部実装を直接知らない | 同じ境界を維持できる |
| 承認は確定し、後からメールを送るか | KOIKIの正式なLevel 1範囲では、耐久的なコミット後非同期連携を提供しない | コミット後の副作用を独立して実行する候補になる |
| 送信時にアプリが停止しても未処理を残せるか | Level 1の同期イベントだけでは、この約束はできない | publicationをDBに記録し、未完了を後で見つけられる |
| 重複せず必ず一度だけ送れるか | 対象外 | Level 2だけでは保証しない。再実行による重複を前提に送信先まで冪等化する |
| 障害後に自動で安全に復旧するか | 対象外 | Level 2導入だけでは成立しない。複数instance、停止確認、再送方式、運用者の判断が必要 |

Level 1の「できない」はSpring一般の技術的な不可能を意味しない。**現行KOIKIが正式に採用・保証するLevel 1の範囲**を指す。素の非同期リスナーや外部I/Oを同期リスナーへ加えても、下記の業務上の約束を満たしたことにはならない。Level 2の採用時も、承認などの業務成立条件は同期のまま扱う。

### 業務例

| 場面 | 成功条件 | KOIKIでの位置づけ |
|---|---|---|
| 部門を廃止する | 未処理の経費申請があれば廃止を拒否する。廃止と監査も確定しない | **Level 1で実証済み。** `master`からの同期イベントを`expense`が確認し、拒否時にロールバックする。Phase 3 DoD 3-2 / 3-3 |
| 経費申請を承認する | 承認状態と業務監査を同じ取引として確定する | 同期の業務処理とPhase 2の業務監査。通知の成否から切り離してよいかは別の要件判断 |
| 承認メールを送る | メール障害では承認を取り消さず、後で送る。二重通知は避けたい | **Level 2のPhase 4計画例。** 配信の保存・再送に加え、送信先の冪等契約と運用が必要。現時点でReferenceにも実案件にも正式提供していない |
| 精算から仕訳・会計連携を行う | 精算確定後に処理し、遅延・失敗時の責任を決める | Phase 4の`accounting`構想。非同期を要件とするならLevel 2の判断と別途MyBatis adoption判断が必要。どちらも未承認 |

Level 2は通知があるアプリすべてに一律適用するものではない。たとえば承認メールが不要なら、この連携自体を設けない選択がある。必要でも耐久配信・再送が業務上不要なら、要件と別方式を明示して設計判断する。KOIKIの現行規約では、無保証の非同期をLevel 1の正式提供として扱わない。

## 3. Level 2を「業務で使える」状態にする条件

Level 2のpublication記録は、**後続処理を忘れないための土台**である。送信の成功や重複防止、運用上の復旧まで自動的に完成するわけではない。

| 業務上の約束 | 必要な実装・運用と主な責任 | PL2で確かめた範囲／残ること |
|---|---|---|
| 承認はメール障害に巻き込まれない | 承認・監査と通知を分離する。対象イベントと受け手を決める。Referenceなら`expense` / `notification`が業務を所有 | Toolingで通知失敗後も元の取引が確定することを確認。正式ReferenceのDoD 4-1実演は未実施 |
| 停止後も送信待ちを失わない | publication用DB schema、migration、保存先の所有者、再起動・再送の入口を決める | JDBC / JPA両storeで停止・再起動・完了までを検証。正式Starter / Reference統合と複数instance運用は未実施 |
| 再送しても二重通知しない | イベント識別子と送信先の冪等key契約、受理したか不明な場合の照合方法をApplication / providerが決める | keyを認識するstubでは1回、認識しないstubでは2回送信された。実providerの保証は未確認 |
| 同時に複数の復旧担当が動いても安全 | 通常処理と復旧処理の競合を防ぎ、旧processの停止を確認し、対象を再照合する | 専用復旧worker間の排他は確認。通常listenerとの競合、停止確認の真正性、lock喪失を検知する前の競合窓は残る |
| 滞留を発見して復旧できる | FAILED件数・滞留時間、alert、復旧権限・Audit、担当者と復旧期限を決める | Toolingの状態・metricと手動復旧入口を検証。実際の監視先、当番、SLA、訓練は未決定 |
| 後から原因と経緯を追える | イベント・publication・再送・requestの相関、秘密情報を出さないlog、保存期間と完了記録の清掃を決める | Toolingで相関とパージを検証。正式OpenTelemetry連携と運用ポリシーは未実施 |

Spring Modulithのpublicationは処理失敗時の記録を残すが、起動時の未完了再公開は既定で有効ではない。複数instanceで単純に有効化すると同一処理が重なる可能性がある。再送方式は配置と運用に合わせて選ぶ必要がある（[Spring Modulithイベント文書](https://docs.spring.io/spring-modulith/reference/events.html)、[設定一覧](https://docs.spring.io/spring-modulith/reference/appendix.html)）。

## 4. なぜPL2では検証を重ねたのか

当初のPhase 4 DoDは「メール障害でも承認成功」「停止後の再配信」「二重通知防止」「滞留の観測・再送」「完了記録の清掃」「ログ相関」を求める。特に**停止後の配信（4-2）と二重通知防止（4-3）**が核心と定められている。これは単にLevel 2のライブラリを追加しただけでは判定できない。

そのためPL2では、業務から見える失敗を一つずつ作った。

1. 通知が失敗する：承認が取り消されず、未完了が残るか。
2. 送る前に停止する：再起動後に失われず送れるか。
3. 送った後に停止する：受理結果が不明でも重複を抑えられるか。
4. 同じ処理を複数instanceで復旧する：同時送信しない根拠があるか。
5. 担当者が再送する：誤った対象・古い状態・権限なしの操作を止められるか。
6. 失敗が長く残る：検知、追跡、清掃を実際に行えるか。

この検証で**技術的に成立した部分と、安全性・運用の未解決部分が分かった**。結果は非配布Toolingの局所試験であり、実provider、正式Reference、実案件運用の受入結果ではない。複数instanceの通常処理と復旧の競合が残るため、現在の復旧runbookは運用採用前の草案である。

## 5. アプリチームと確認する判断、今後の分岐

業務アプリチームには、技術名より先に次を確認する。

| 確認事項 | 具体的な回答の例 |
|---|---|
| 承認など元の操作を何が止めるべきか | 「未処理申請がある部門廃止は拒否」「メール障害では承認を取り消さない」 |
| コミット後の副作用は本当に必要か | 通知先・通知目的・送信しない場合の影響を特定する |
| 遅延・喪失・重複の許容値は何か | 何時間以内に必要か、再送時の二重送信を許容できるかを決める |
| 送信先と運用は誰が所有するか | providerの冪等契約、障害照会、alert受信者、復旧担当・代行者を決める |
| 案件間で何を共通化する必要があるか | 1件のReference実演で十分か、複数Consumerへ共通契約が必要かを判断する |

これらの回答に応じ、P4-Fでは**S0：Level 1を維持して見送る**、**S1：対象を限定して実証する**、**S2：共通基盤として提供する**を比較する。現時点でS2の独立した利用先と実案件の通知・運用要件は確認できていない。S0なら当初Phase 4 DoD 4-1〜4-5・4-12は未達として、延期・変更と依存作業の再計画をArchitecture Ownerが判断する。S1でも各アプリのprovider契約、当番、費用、受入は案件ごとの判断に残す。PL2時点でGate P4-Fは未設置・未通過であり、Phase 4 production開始も未承認である。

**業務アプリチームへの要約:** Level 1は「相手の判断まで終えてから業務を確定する」ために使う。Level 2は「業務を確定した後の処理を、障害を越えて届ける必要がある」場合の候補である。後者を約束するには、再送時の重複、滞留監視、復旧責任まで含めて案件ごとに成立させる必要がある。
